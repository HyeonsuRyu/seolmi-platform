# 0001. 단일 앱 + HTTPS REST 유지, gRPC 미도입

- 상태: 채택
- 날짜: 2026-09-11
- 결정자: 류현수(개발 리드), 조윤빈(팀장)
- 발단: "gRPC 없이 다 HTTPS로 통신하나요?" (류현수)

## 맥락

질문의 전제를 먼저 정리해야 한다. **gRPC는 HTTPS의 대안이 아니다.**
gRPC도 HTTP/2 + TLS, 즉 HTTPS 위에서 돈다. 층위가 다르다.

| 층 | 우리 선택 | gRPC를 쓸 경우 |
|---|---|---|
| 전송 보안 | TLS (HTTPS) | TLS (HTTPS) — 동일 |
| 전송 프로토콜 | HTTP/1.1 | HTTP/2 (강제) |
| 메시지 형식 | JSON | Protobuf (`.proto` 스키마 별도 관리) |
| 호출 단위 | 같은 프로세스 안의 파이썬 함수 호출 | 네트워크를 건너는 RPC |

따라서 실제 질문은 "서비스를 쪼개서 내부 통신 규약을 따로 둘 것인가"이다.

설미 플랫폼은 FastAPI **단일 앱(모놀리식)** 이다.
`app/api/b2c/` 가 `app/domains/cs/` 를 부를 때 네트워크를 타지 않는다.
프로토콜이 개입할 자리 자체가 없다.

3면 분리(B2B · B2C · 관리자)는 **폴더 구조와 JWT 권한 분리**이며
서버 분리가 아니다. 3면이 곧 서비스 3개는 아니다.

## 결정

1. 외부 노출 구간은 전부 **HTTPS + REST / JSON**.
2. 모듈 간 통신은 **파이썬 함수 호출**. 내부 RPC 계층을 두지 않는다.
3. **gRPC는 도입하지 않는다.**
4. `app/domains/` 는 도메인별로 갈라 둔다 — 나중에 쪼갤 때 이 경계를 서비스 경계로 쓴다.

## 근거

| 항목 | 내용 | 근거 | 리스크 |
|---|---|---|---|
| 내부 RPC 지점 | 없음 | 서비스가 1개. 구현 인원 2명(류현수·조윤빈) | 트래픽 증가로 쪼갤 때 경계를 다시 그어야 함 → 결정 4번으로 완충 |
| 브라우저 호출 | gRPC는 브라우저에서 직접 못 씀. gRPC-Web + 프록시(Envoy 등) 필수 | B2C·관리자 화면이 Jinja2 서버 렌더링 + fetch (추정) | 도입 시 운영 컴포넌트 1개 추가 — 2명이 감당할 양이 아님 |
| 외부 연동 | PG, 네이버 스마트스토어, LLM API, 축산물이력제 — 모두 HTTPS REST만 제공 | 우리가 고를 수 있는 문제가 아님 | 없음 |
| API 문서 | REST면 FastAPI가 `/docs` 를 자동 생성 | 문서 유지 비용 0 | gRPC로 가면 `.proto` 를 손으로 관리 |
| 성능 | Protobuf가 JSON보다 빠른 건 사실이나, 병목은 DB 쿼리와 LLM 응답(초 단위) (추정) | 직렬화 이득은 밀리초 단위 (추정) | 오픈 전이라 실측 불가 — 부하 테스트로 검증 |
| 실시간 | 필요해지면 gRPC 대신 WebSocket 또는 SSE로 충분 | CS 채팅 스트리밍 정도가 후보 | 없음 |

## 재검토 조건 — 하나라도 걸리면 이 결정을 다시 연다

- 도메인 하나를 별도 서버로 분리한다 (이미지·영상 처리, 재고 배치 작업 등)
- Python이 아닌 언어로 짠 내부 서비스가 생긴다
- 내부 호출이 초당 수천 건 규모가 되고, **실측에서** 직렬화가 병목으로 잡힌다

세 조건 모두 오픈 이후 문제다. 지금 도입하면 프록시·`.proto`·툴체인 유지비만 먼저 낸다.
